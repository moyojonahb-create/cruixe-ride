## Isolation design and operating procedure

1. Approve an existing dedicated host or paid creation with an agreed budget, owner and destruction/retention policy. Verify SSH host fingerprint from an independent channel. Use a distinct test account/project/network and no Railway/Supabase production membership, snapshots, data copies or credentials. Permit SSH from the operator IP; expose no public database/Redis ports.
2. Review a source-only export manifest that includes the dirty-tree P0.1/P0.2 files and required untracked tests/drafts, rather than exporting HEAD alone. Exclude .env, .git, tokens, keys, Android signing material and local secrets; hash the manifest and inspect secret-scan results. Transfer only after the remote destination is approved. No source was uploaded during this task.
3. Pre-fetch pinned images and dependency caches in a separate build stage with no production credentials. Record image digests, PostgreSQL/Redis/Go/Node/extension versions. Choose Redis with the existing production adapter protocol; a compatible replacement needs explicit protocol/PubSub/expiry evidence, not a compatibility label alone.
4. Create a unique task-labeled disposable pod/network on Linux. Use a Docker internal-only network with no external default route. Run the test runner and Redis sharing PostgreSQL's network namespace so every test DSN can remain a literal loopback IP. The runner thus reaches PostgreSQL at127.0.0.1:5432 and Redis at127.0.0.1:6379 while the namespace has no production route. Do not attach a second internet-facing network, host network, Docker socket or host credentials to the runner. Verify blocked external egress from inside the actual runner before any fixture DDL. No such pod/network has been created or verified yet.
5. Use fresh random credentials, named database/role guards and randomly isolated fixture schemas. Prefer tmpfs for fixtures and a dedicated bounded cache for dependencies; never mount application production .env. Minimal database profiles are cruize_p01_test, cruize_p02_test and cruize_p03_test. The new P0.3 role must be exactly cruize_p03_test, with no CREATEDB/CREATEROLE/BYPASSRLS/SUPERUSER and no rights on public/auth application tables. Grant only required database CREATE for its own random fixture schema and read access to the test identity marker. Owner bootstrap creates cruize_test_guard.metadata(key PRIMARY KEY,value) with environment=p03-disposable-v1 and grants marker SELECT. Bootstrap runs only after independently validating the new disposable host/container identity.
6. Tests must reject nonliteral-loopback or nonlocal fallback DSNs and wrong database/role/marker before fixture writes. No application .env auto-load, ambiguous default DSN, DNS host alias or production tunnel is allowed. A localhost SSH forward alone is not proof of isolation. Prefer running tests inside the verified isolated pod; Windows SSH tunnels require independently verified target identity and the same database/role/marker guards. The existing four P0.1/P0.2 tests have their own host/database guards and need external network/credential isolation too.
7. Keep the Redis marker in a dedicated namespaced key and isolate Pub/Sub using a random channel for each run: Redis database numbers do not isolate channels. The real-Redis fixture must verify this identity before expiry/disconnect tests. Never run FLUSHALL, global CLIENT KILL or redis-cli against a default endpoint. Target only a task-owned subscriber/container for interruption.
8. Run existing fixtures and the P0.3 conformance command below sequentially. Capture leaf PASS/FAIL/SKIP, real lock contention, schema/index/trigger/grant/RPC definitions, exact error codes, accepted money, role identity and resources. Verify effective candidate schema, not all source migration history. Do not run guarded draft SQL artifacts as migrations.
9. Preserve failure evidence and remove only task-owned fixture schemas/containers after validating unique labels/IDs. Keep user-existing workloads and volumes untouched. Verify no task job or port remains. Budget and approve paid-host retention separately; do not assume a stopped machine stops billing. Nothing was provisioned here, so there is no task infrastructure to clean up.
