## Proposed storage invariants (not DDL)

Use drivers.id as reservation identity, with explicit drivers.user_id auth mapping. Proposed active_driver_reservations has one row per driver (driver_id primary/unique key), ride_id unique, stable assignment identity, exact accepted terms/reference and server timestamps. It represents active ownership, not a Redis lease. Never expire a live trip reservation merely because presence or a socket disconnects. Terminal cancellation/completion releases only the matching driver/ride/assignment row within the state-transition transaction; stale release cannot free a later assignment. Retain historical assignment/consent evidence separately from this active projection.

After commit: every accepted/arrived/in_progress ride has exactly its matching active reservation; every active reservation points to its current active assignment; no driver owns two active rides and no ride has two active drivers. Eligibility is rechecked at claim time; later driver suspension must deny protected actions without silently freeing a live trip or cancelling it through an unapproved policy. Uniqueness alone does not enforce state/reservation consistency: a shared primitive plus effective write restrictions and/or reviewed database enforcement is required. Whether scheduled rides reserve capacity is a product decision; preserve current behavior until resolved. Existing duplicate assignments must be detected and remediated through reviewed data ownership before any uniqueness DDL.

Accepted fare comes from the rider-selected current proposal or an explicitly allowed fixed-fare contract. Copy canonical exact numeric/minor-unit amount and currency, consent/reference and agreed term version without float64 conversion. Choose supported currency/exponent/range and rounding policy with existing money authority; do not invent new fees. Immutable proposal history belongs to P0.4; P0.3 must at least bind a stable accepted source and protect it from concurrent term edits. Receipt/outbox storage ownership must coordinate with P0.5 rather than create incompatible tables independently.

## Transaction and deterministic locking protocol

Candidate order: actor/operation/idempotency receipt -> ride rows sorted by ID -> driver/reservation lock targets sorted by drivers.id -> offer rows sorted by ID -> applicable proposal rows. A command uses the relevant subset; it must never acquire a driver/ride lock after an offer lock. Use an existing drivers row as the serialization anchor, because a SELECT FOR UPDATE of an absent reservation row cannot lock that absence.

1. Validate signed actor, operation, IDs, canonical request hash and command intent. Scope receipts by actor+operation+key. Insert/lock the receipt before resource locks; same key/body returns the stored committed result, changed body conflicts. A receipt is not implemented by this design.
2. Resolve immutable candidate IDs without relying on that lookup as authority. Lock the ride, verify owner/mode/state, then the candidate driver row. If offer identity was discovered before locking, lock the offer next and recheck its association/driver/terms; restart safely with the same command identity if discovery no longer matches. Do not discover and lock a second ride in arbitrary order after already holding the first.
3. Recheck driver eligibility, current reservation, request/proposal versions, permitted ride/offer states and expiry using fresh PostgreSQL time after lock waits. NOW() is transaction-start time, so it alone cannot implement expiry-after-wait. No external provider/network calls while holding locks; prerequisite attestations must have defined validity.
4. Claim the database reservation; update exactly one ride and selected offer, close competing pending offers in deterministic order, and persist accepted terms/command result atomically. Map expected uniqueness/serialization conflicts to stable errors; never expose SQL detail. Lock and release each other mutated relation in a reviewed global order.
5. Roll back all state/reservation/receipt changes on any failure. Emit only committed posttransaction effects. Current best-effort sockets are not durable events; outbox/P0.5 is still needed to close commit/publish/response crash gaps.
6. Retry only bounded deadlock/serialization failures with the same actor/operation/key/hash. An ambiguous commit requires receipt lookup/replay, not a different direct/RPC mutation. Redis dispatch-lock failure may degrade discovery but cannot change database acceptance authority.

Cancellation/start/completion/reassignment must follow the same relevant lock order and reservation ownership rules. Reassignment has no approved product workflow yet: do not silently repurpose cancelled/history rows. Financial/account locks, if a future acceptance command needs them, require an explicit compatible order with the existing wallet authority before implementation.

### Authoritative acceptance prerequisite

The required contract is one authenticated `AcceptOfferAndAssignDriver` application command, reached by Go and every retained RPC/direct compatibility adapter, with no independent fallback mutation. Its server-derived actor must own rides.user_id, offer must belong to that ride and the immutable consented revision, ride must be eligible (normally pending; scheduled policy requires explicit approval), offer pending/unexpired, and the mapped drivers.id must remain approved/eligible after all lock waits. No client body may override driver identity or agreed money. Direct fixed-fare acceptance requires an explicit mode/consent contract; it cannot silently bypass negotiated acceptance.

A single transaction owns the actor/operation/key receipt, all validation-dependent locks, unique driver claim, immutable accepted agreement, ride transition, selected/competing offer transitions and durable event intents. Common order: receipt identity -> sorted ride rows -> existing driver serialization rows in sorted ID order -> all affected offers in sorted ID order -> immutable terms. Do not lock a missing reservation row as the serialization anchor. Every cancel/start/complete/reject/withdraw/expiry path must follow the same order/subset; no driver-first command may subsequently acquire a ride row. Do not lock an unrelated driver's active ride after holding a driver anchor; return DRIVER_BUSY instead. Bound/retry deadlocks only for retryable infrastructure errors with the same idempotency identity. Re-read clock_timestamp/eligibility after waiting. Cancellation/complete release only WHERE driver_id/ride_id/assignment_id all match, in the same terminal-state transaction. Historical agreement/driver identity survives release.

Receipt request hash binds canonical actor/operation/ride/offer/revision/exact terms, excludes gateway identity, stores stable domain result, and replays the same response. Altered input under the same key conflicts; uncertain commit must reconcile the receipt. Receipt scope, deterministic denials and durable event intents must agree with P0.5; there is no outbox proof in this fixture. Notification delivery follows commit and cannot authorize a second writer. Typed errors and compatibility envelopes still require approval (INVALID_STATE, DRIVER_BUSY, DRIVER_INELIGIBLE, OFFER_EXPIRED, IDEMPOTENCY_CONFLICT and existing auth/masking semantics).

Unique constraints in the fixture test driver PK/ride UNIQUE/assignment UNIQUE and composite agreement tuple references; physical assertions independently verify active ride, driver, agreement, accepted offer, exact price, receipt and reservation consistency. These indexes do not enforce complete state semantics or prevent legacy writers from ignoring reservations. Writer restrictions and all state-changing paths remain an activation gate. Deletion cascades/history, duplicate remediation, product currency/exponents, immutable revisions and effective provider grants remain unresolved.
