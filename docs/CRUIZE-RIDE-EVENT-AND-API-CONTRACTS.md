# Cruize Ride event and API contracts

26 October 2026, Africa/Johannesburg. This document proposes P0.2–P0.5 boundaries; the final P0.2 runtime section distinguishes implemented compatible behavior from future contracts. The `backend/internal/contracts` package contains dependency-free structural contracts and tests only; it is **not wired into runtime**. No receipt table, outbox, reservation, proposal history, broker, payment integration or applied migration is established by this document. P0.1 handler fixes do not satisfy these later guarantees.

Evidence: existing source in `backend/internal/rides/handler.go`, `backend/internal/business/handler.go`, `backend/internal/websocket/{authorizer,manager}.go`, `backend/internal/geo/service.go`, `backend/internal/dispatch/{service,repository}.go`, `src/lib/{offerHelpers,rideMatching,backendSocketClient}.ts`; the phase-two architecture audit, feature comparison, implementation plan, bidding architecture recommendations and verified feature-gap reports under `C:\REA-Workspace\Reports`. Reports are recommendations reconciled with source, not deployed-schema evidence. No inDrive private backend behavior is inferred or reproduced.

## Service authority and compatibility

The target is one modular Go application-service authority, with existing HTTP/RPC shapes retained as compatibility adapters where feasible. Interface sketch:

```go
type RideCommands interface {
    CreateRide(context.Context, Actor, CreateRideInput) (RideResult, error)
    SubmitDriverOffer(context.Context, Actor, SubmitOfferInput) (OfferResult, error)
    CounterOffer(context.Context, Actor, CounterOfferInput) (OfferResult, error)
    AcceptOffer(context.Context, Actor, AcceptOfferInput) (RideResult, error)
    RejectOffer(context.Context, Actor, RejectOfferInput) (OfferResult, error)
    WithdrawDriverOffer(context.Context, Actor, WithdrawDriverOfferInput) (OfferResult, error)
    CancelRide(context.Context, Actor, CancelRideInput) (RideResult, error)
    AssignDriver(context.Context, Actor, AssignmentInput) (RideResult, error)
    StartTrip(context.Context, Actor, TripInput) (RideResult, error)
    CompleteTrip(context.Context, Actor, TripInput) (RideResult, error)
}
```

These DTOs are a specification, not compiled service implementations. `WithdrawDriverOffer` is the tenth command: driver withdrawal must remain distinct from rider rejection. `AssignDriver` is an internal operation called within the acceptance transaction, never a second independently committed step.

Authenticated subject and role derive from verified credentials. Never trust body `rider_id`, `driver_id` or admin flags. Current identity conventions differ: `rides.user_id` is rider auth ID; `rides.driver_id` is driver row ID; `offers.driver_id` is driver auth ID. Explicit conversion and ownership checks are required. `offers` represents negotiated bids; `ride_offers` represents dispatch invitations. No rename or merge is implied.

Every command has actor-scoped idempotency key, operation, canonical request hash, request/trace IDs, expected aggregate/offer version when applicable and resource IDs. Same actor/operation/key/body replays the committed response; altered body returns conflict. Do not fallback to another mutation authority after auth failure, timeout or an ambiguous commit. Query/replay the same identity. Any retained public RPC must enforce equivalent consent, eligibility, locking and receipt semantics, using a shared database mutation primitive or an explicitly reviewed retirement plan.

Proposed lock order: receipt → ride(s), sorted by ID → driver/reservation rows, sorted by identity → offers, sorted by ID → proposal rows. All acceptance, cancellation, withdrawal, rejection and expiry writers use this order. Creation inserts its new ride. Do not hold one ride lock then discover and lock another unsorted. Enforce driver active-assignment uniqueness in PostgreSQL; rider uniqueness remains a documented policy decision. Redis cannot provide final assignment authority.

Each successful mutation commits state, agreed terms, receipt, audit/domain events and outbox rows in one transaction. Recheck state, eligibility, revision and expiry **after** locks using fresh database time. No external network calls inside the transaction. Bounded retry on serialization/deadlock keeps the same command identity. Existing handler transactions do not yet implement this full contract.

## Command matrix

All rows inherit the transaction, lock and idempotency rules above. Events listed are proposed durable names. Realtime occurs only after commit and only to authorized recipients; it does not establish command success.

| Command | Actor and allowed starting state | Validated input and atomic effect | Durable events / recipients / specific errors |
|---|---|---|---|
| CreateRide | Authenticated rider; new aggregate | Coordinates, bounded addresses, service area/type, payment method, exact amount/currency, passengers and schedule. Persist `pending` or supported `scheduled`, request revision and expiry. | `ride.created`; rider and sanitized eligible-driver discovery. `INVALID_INPUT`, `SERVICE_UNAVAILABLE`, payment-method denial. |
| SubmitDriverOffer | Approved eligible driver; ride `pending`, unexpired | Ride/revision, exact proposal terms, currency, bounded ETA/message. Resolve approved vehicle; reject stale request revision; persist offer and initial immutable proposal. One pending offer per driver/ride; expired predecessor must be terminalized transactionally. | `offer.submitted`; owning rider and submitting driver. `DRIVER_INELIGIBLE`, `STALE_VERSION`, `OFFER_EXISTS`, `RIDE_EXPIRED`. |
| CounterOffer | Owning rider or offer driver; pending ride/offer; responding to counterparty | Exact current proposal/revision, new exact amount/currency, bounded expiry. Append proposal; atomically supersede current pointer. No in-place agreed fare rewrite. | `offer.countered`; counterparties only. `STALE_VERSION`, `OFFER_EXPIRED`, `INVALID_STATE`. Disabled until storage/policy gate passes. |
| AcceptOffer | Counterparty of current proposal; initial driver bid accepted by owning rider | Ride/offer/proposal IDs and versions; never a client amount override. Recheck eligibility, expiry, consent, request revision; assign within this transaction, snapshot exact fare/currency, close losing offers. | `offer.accepted`, `ride.assigned`, losing-offer closure; participants and affected losing drivers with private terms filtered. `DRIVER_BUSY`, `CONSENT_REQUIRED`, `STALE_VERSION`, `OFFER_EXPIRED`. |
| RejectOffer | Owning rider; pending ride and offer | Matching ride/offer IDs, version. Close selected offer without changing ride assignment or globally freeing driver. | `offer.rejected`; rider and selected driver. `INVALID_STATE`, `STALE_VERSION`, `FORBIDDEN`. |
| WithdrawDriverOffer | Driver who owns pending offer; ride pending | Matching IDs/version, bounded reason. Close own offer; cannot withdraw a winning assignment through this command. | `offer.withdrawn`; counterparties. `INVALID_STATE`, `STALE_VERSION`. Preserve legacy decline adapters explicitly. |
| CancelRide | Owning rider, assigned driver, or permission-scoped admin; allowed nonterminal states by actor policy | Ride/version, bounded reason; server fee policy. Guard state, close pending offers, record cancellation/fee decision, release active reservation and audit atomically. | `ride.cancelled`; participants followed by room revocation. `INVALID_STATE`, `FORBIDDEN`, `STALE_VERSION`. Completed/cancelled/expired immutable. |
| AssignDriver | Internal acceptance service; ride pending; valid accepted proposal or explicit fixed-fare dispatch authorization | Driver row/auth mapping, vehicle, consent reference, exact immutable terms. Claim durable reservation and assignment; no external public driver-ID override. | `ride.assigned`; assigned participants, dispatch projection. `DRIVER_BUSY`, `DRIVER_INELIGIBLE`, `CONSENT_REQUIRED`, `INVALID_STATE`. |
| StartTrip | Assigned driver; `accepted` or `arrived` for current compatibility | Ride/version; assignment ownership and any product-approved verification requirements. Guard transition to `in_progress`, store server start time. GPS alone cannot authorize start. | `trip.started`; participants. `FORBIDDEN`, `INVALID_STATE`, `STALE_VERSION`. |
| CompleteTrip | Assigned driver; `in_progress` | Ride/version; no arbitrary fare/payment-status override. Complete once, store server time, release reservation and request settlement atomically. | `trip.completed`, `settlement.requested`; participants then room revocation. `INVALID_STATE`, `STALE_VERSION`. Completion does not mean payment settled. |

Cancellation policy is unresolved: existing Go routes and SQL fallback disagree on `scheduled`, `arrived`, `in_progress`. P0.1 preserves permitted nonterminal transitions per route while forbidding terminal overwrite. A unified policy requires an explicit decision; admin permission does not automatically authorize terminal history edits. Reassignment after cancellation requires a new linked request until an assignment-attempt model is approved. Direct acceptance requires an explicit fixed-fare mode; absence of bids is not consent.

Common errors: 400 `INVALID_INPUT`; 401 `UNAUTHENTICATED`; 403 `FORBIDDEN`/`DRIVER_INELIGIBLE`; 404 `NOT_FOUND` (mask inaccessible resources consistently); 409 `INVALID_STATE`/`STALE_VERSION`/`IDEMPOTENCY_CONFLICT`/`DRIVER_BUSY`; 410 `OFFER_EXPIRED`/`RIDE_EXPIRED`; 503 `TEMPORARILY_UNAVAILABLE`. Response includes stable code, request ID and safe canonical version/state where authorized. Do not label every 404/409 as expired. Ambiguous commit is an uncertain result requiring reconciliation, not permission to create a new command.

## Money, events and recovery

Money is signed `int64` minor units plus supported currency. Command-specific positive/nonnegative bounds, exponent and rounding come from server policy. Validate overflow at adapters; never pass accepted terms through `float64`. Existing numeric schemas require a separately reviewed exact conversion/currency migration; the package does not change them.

Proposed durable envelope: `event_id`, `command_id`, `aggregate_id`, monotonic `aggregate_version`, `type`, `schema_version`, server `occurred_at`, bounded object `payload`. Unique event identity is stable on retry; versions are allocated transactionally. If a command emits multiple events, allocate successive aggregate event versions in that transaction. Node-local WebSocket sequence is not this version. The structural validator does not verify event authenticity or domain payload schemas. Consumers reject/quarantine unsupported schemas before applying effects.

Outbox publisher leases pending rows, publishes and marks responsibility transferred; crash after publication can duplicate the event. Broker success means durable responsibility, not client delivery. Consumer effect plus deduplication identity commit atomically. Poison events have bounded retry, quarantine and alerting; they cannot be silently discarded. Retention, replay cutoff, recovery lag and deletion policies need explicit ownership and measurements before release.

Redis Pub/Sub remains transient fanout. Streams/Kafka are adapter choices after demonstrated retention/throughput requirements. A single consumer group distributes messages; it does not broadcast every event to every gateway. Route events to gateways holding authorized sessions, or define separate independent subscriptions. Revocation must reach every affected gateway, plus lease/revalidation must limit damage when delivery is missed. Durable broker availability cannot replace PostgreSQL state/authorization.

Reconnect requires authenticated canonical snapshot with version/cursor and a race-free subscription handshake: authorize and buffer live events, read snapshot/watermark, replay strictly newer retained events, then release buffered events with dedup/gap checks. If replay retention is exceeded, require a new snapshot. Reauthorize token expiry, session revocation, suspension and participant reassignment on existing connections, not only room join. Terminal snapshots remove old room entitlement even if a revocation packet was missed. Queue limits disconnect slow clients with explicit resync behavior. Never expose unrelated private offers or precise pre-assignment rider locations.

## Geo, routing and mobile boundaries

Authenticated location ingest binds driver row/auth identity to a server-issued device session/epoch, monotonic per-session sequence, sampled time and server received time. Reject unknown/old epochs before comparing sequences; client-supplied high epoch is not trusted. Reject nonfinite/out-of-range coordinates, negative accuracy, stale/future samples and impossible movement according to reviewed policy. Persist authorized sample/projection conditionally before fanout. Timestamps/sequence checks do not prove physical authenticity; fraud signals and accuracy limits remain separate. The contract tests validate freshness and ordering only.

Redis GEO is a candidate cache; PostgreSQL eligibility, service geofences and assignment authority filter results. Routing/distance/ETA adapters receive validated coordinates and expose provider/time/freshness; unavailable routing must not invent trusted ETA or authorize payment. Geofence changes are versioned, permission-scoped, audited commands with validation and rollback. No H3, PostGIS or alternative routing stack is installed; adopt after measured query/coverage needs and migration review.

Keep React/Capacitor. Native Android plugins are warranted for measured background-location/foreground-service reliability, notification delivery, secure key storage and permission lifecycle requirements. A location plugin emits the same authenticated session/sequence contract; native execution grants no extra server authority. Document battery, Android service restrictions, denied/background permissions, offline batches, mock-location signals, device clock skew and app termination tests before release. No Flutter/Kotlin platform rewrite is authorized.

## Payments, ledger, risk and administration

Settlement has independent `pending/confirmed/failed/unknown` outcomes; provider acknowledgement is distinct from reconciliation confirmation. Cash records expected receivable and verified collection separately; rider/driver assertions cannot silently mark reconciled. EcoCash/local methods use a credential-isolated adapter with stable payment/idempotency reference, authenticated callbacks, exact amount/currency comparison and reconciliation query. Never retry an uncertain debit under a fresh identity. No real credentials, provider calls or transactions are introduced.

Future ledger postings have immutable entry IDs, source payment/command, accounts, exact currency/amount and balanced debit/credit totals **per currency** within one transaction. Unbalanced postings fail atomically; duplicate external event cannot post twice. Reversals append compensating entries, never edit history. Balance/overflow and debit-credit tests need the actual ledger service; no accounting correctness is claimed by these adapter types. Reconciliation maps external statement references to internal settlement/ledger records with explicit unmatched/duplicate/amount-conflict states.

Disputes preserve trip/payment history and have permission-scoped transitions, evidence access audit and retention. Identity verification stores provider reference/status and minimal necessary personal data; client assertion cannot grant verified-driver eligibility. Risk events carry stable event ID, subject reference, rule/model version and decision provenance; analytics/risk projections cannot directly mutate ride assignment or money. Manual actions use explicit authorized commands. RBAC separates support read, dispute action, payout adjustment, driver approval and geofence management, with actor/reason/before-after references and request ID in tamper-evident audit storage. Production role/grant review remains required.

Analytics subscribes to minimized domain events via the broker boundary and idempotently builds replaceable projections. No raw precise GPS, credentials, identity documents or unrestricted PII in generic event/log streams. Warehouse/ClickHouse/Kafka deployments are deferred; schemas, retention, access control and throughput gates precede adoption.

## P0.2 runtime compatibility contract

The earlier versioned event envelope and durable recovery sections are future contracts. Implemented runtime messages retain their existing event names and payloads; no event ID, aggregate version or durable replay cursor was fabricated.

- GetRide is authenticated and participant-scoped, including terminal reconciliation. driver_id remains the driver database row ID; additive driver_user_id is the assigned driver's auth subject. Unavailable/foreign rides return 404.
- ride_<id> joins authorize rides.user_id or the eligible current driver resolved through drivers.id. Owners: pending if unexpired, scheduled, accepted, arrived, in_progress. Assigned driver: accepted, arrived, in_progress. Unknown/terminal/expired pending rides deny membership. Join errors reveal no ride details.
- driver_location identifies driver_id as the authenticated driver subject, includes ride_id/room and additive updated_at from server acceptance, and requires current active assignment and current recipient membership. This timestamp is not a device epoch, proof of physical location or durable sequence. Browser rejects unrelated scope/driver, invalid coordinates, timestamps older than 120 seconds, more than 30 seconds in the future, or non-increasing observed times within its subscription.
- ride_cancelled/ride_completed may reach only canonical final participants when the database confirms the matching terminal state; this narrow final-event exception never grants membership or location access. Delivery is best effort, with canonical API reconciliation after revocation.
- room_revoked, room_user_revoked and join_room_denied discard browser room intent and references. room_joined cannot clear a tombstone. A fresh authenticated connection must still pass current database authorization, while automatic reconnect retains revoked-room denial.
- ride_snapshot is a client-local event produced only from the authenticated API response, never accepted as a WebSocket snapshot. Snapshot precedes join, but is not an atomic versioned replay handshake. Lost updates reconcile through subsequent canonical reads; mutations are not replayed.
- ride_offer is an existing eligible-driver dispatch request. It is not a public negotiated-offer feed. Existing negotiated bid readers retain their APIs and RLS dependencies. Acceptance now sends existing ride_accepted notification to the rider and actual assigned driver; no agreement/price/expiry rules changed.

JWT exp is mandatory at socket handshake and enforced during the connection. Verified session_id is metadata; the optional server session authorizer requires verified deployed semantics before wiring. Role/assignment checks do not certify user-session revocation. Database errors fail closed. Revocations fence concurrent joins and queued delivery; final checks cannot retract bytes already in transit. Redis sequence remains per sender node, not an aggregate revision. Full versioned recovery, receipts and transactional outbox stay in P0.5.

## 27 October: assignment command/repository review contracts

The six requested operations are specified in docs/p03-drafts/assignment-contracts.go.txt and the P0.3 preparation matrix: ReserveDriver, ReleaseDriverReservation, AcceptOfferAndAssignDriver, RejectConflictingAssignment, CancelAssignedRide and CompleteAndReleaseDriver. Only acceptance/cancellation/completion are application command entry points; reserve/release/conflict rejection are internal Tx methods, never independent public commits. RejectConflictingAssignment returns a conflict without modifying the winner and is distinct from rider RejectOffer.

Receipt -> ride -> driver/reservation -> affected offers -> terms is the common sorted locking order. Lock all offers that will change before bulk status writes; submit/counter/expiry/rejection writers must coordinate on the parent ride so unreviewed direct inserts/updates cannot bypass acceptance. Idempotency keys scope to actor+operation, hashes exclude gateway/trace details, exact-money DTOs exclude float64 and body authority. Known deterministic rejections commit their stable receipt result; SQL/infrastructure failures roll back. Ambiguous commit reconciles the same key. Suspension does not release a live reservation automatically.

Proposed durable intents are ride.assigned, ride.cancelled, trip.completed and matching reservation release, with stable event/aggregate identities. They require the coordinated P0.5 storage primitive; existing WebSocket names/payloads remain unchanged, and event delivery does not establish command success. Immutable term/version consent remains coordinated with P0.4; no version or provider/session guarantee is fabricated.

The SQL artifact outside migrations aborts before DDL and ends with rollback. It drafts accepted agreement, unique active reservation and actor-scoped receipt structures only; grants/triggers/shared mutation authority/backfill/outbox are deliberately gated. Current Go/RPC handlers remain unchanged pending effective schema/privilege and policy review. New conformance tests have no candidate authority adapter and cannot be reported as real-service success while skipped. Refer to [P0.3 preparation](CRUIZE-RIDE-P03-ASSIGNMENT-PREPARATION.md) and [environment recommendation](CRUIZE-RIDE-INTEGRATION-INFRASTRUCTURE.md).
